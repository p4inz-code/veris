# VERIS Architecture Decision Record (ADR) 016: AI-Assisted Rule Authoring Contract

**Status:** Accepted / Foundational  
**Date:** 2026-09-24  
**Authors:** Autonomous Principal Engineer (Antigravity)  
**Applies to:** `@veris/cli`, `@veris/rules`, `@veris/plugin-sdk`, `@veris/plugins`, `@veris/ai`  
**Supercedes / Refines:** Extends ADR-014 (Plugin Architecture) and ADR-010 (AI Layer Boundaries)  
**Target Milestone:** VERIS V2.0.0

---

## 1. Executive Summary & Purpose

The VERIS platform is built on strict determinism, offline-first analysis, and evidence-first findings. AI models (LLMs) are inherently non-deterministic, probabilistic, and prone to hallucination. Therefore, VERIS strictly prohibits AI from participating in primary detection, rule evaluation, or risk scoring.

However, writing robust, high-fidelity security detection rules in declarative AST format can be time-consuming. Operators often have a clear threat intent (e.g., "detect unauthorized PowerShell encoded command execution with bypass flags" or "flag hardcoded AWS secret keys in configuration files") but need assistance generating:

1. Pure declarative AST condition trees (`PluginRuleLogic`).
2. Comprehensive MITRE ATT&CK, CWE, and NIST compliance mappings.
3. Realistic positive matching and negative non-matching test fixtures.
4. Actionable remediation guidance.

This document establishes the **hard technical architecture, provider contracts, declarative purity boundaries, deterministic validation gates, test generation requirements, and human-in-the-loop promotion workflow** for AI-assisted rule authoring in VERIS.

---

## 2. Inviolable Architectural Principles

1. **AI is an Authoring Assistant, Never a Scanner:**
   AI models NEVER evaluate files during a scan, NEVER produce authoritative security findings, and NEVER calculate risk scores. The live security analysis pipeline remains 100% deterministic and free of LLM execution.

2. **Model Output is 100% Untrusted Data:**
   All candidate rule definitions generated or suggested by an AI model are treated as untrusted JSON input. They must pass rigorous deterministic structural, semantic, and purity validation before being presented to a human.

3. **Strict Declarative Purity (Zero Code Execution):**
   Rules generated by this subsystem are pure AST data structures (`PluginRulePack`). Executable JavaScript predicates, dynamic callbacks, lambdas, `eval()`, `Function()`, and custom functions are strictly prohibited.

4. **Zero Mandatory Network / Offline-First:**
   Rule authoring MUST function completely offline using deterministic offline templates or local models (e.g., Ollama). No cloud provider is mandatory. Target files and evidence are NEVER exfiltrated to remote servers.

5. **No Automatic Promotion:**
   AI-generated rules are emitted as **Candidate Rule Artifacts** (`candidate-rule.json` / `candidate-rule.md`). They CANNOT be automatically loaded into the rule engine or active plugin directories. Promotion requires explicit human command invocation.

## 3. End-to-End Authoring Pipeline

```
  ┌────────────────────────────────────────────────────────┐
  │ Human Operator Intent / Specification                  │
  │ (intent text, evidence category, taxonomy, CWE, etc.)  │
  └───────────────────────────┬────────────────────────────┘
                              │
                              ▼
  ┌────────────────────────────────────────────────────────┐
  │ AI / Template Generation Layer                         │
  │ (prompts.ts + provider.ts: offline template or LLM)    │
  └───────────────────────────┬────────────────────────────┘
                              │ untrusted candidate JSON
                              ▼
  ┌────────────────────────────────────────────────────────┐
  │ Deterministic Validation Gate (validator.ts)          │
  │ - Manifest & Schema Validation                         │
  │ - Declarative Purity Check (checkDeclarativePurity)    │
  │ - Supported Matchers & Operators                       │
  │ - ReDoS & Regex Length Checks (<= 1,000 chars)         │

  ┌────────────────────────────────────────────────────────┐

  └────────────────────────────────────────────────────────┘
```

## 4. Module Specifications

### 4.1 Input Specification (`types.ts`)

The authoring request supports both structured CLI flags and JSON definition files:

```typescript
export interface RuleAuthoringRequest {
  readonly intent: string;
  readonly name?: string;
  readonly category?: RuleCategory;
  readonly evidenceType?: string;
  readonly propertyPath?: string;
  readonly matcherOperator?: PropertyMatcherOperator;
  readonly expectedValue?: unknown;
  readonly cweId?: string;
  readonly taxonomyId?: string;
  readonly severity?: SeverityLevel;
  readonly provider?: string;
  readonly offline?: boolean;
}
```

### 4.2 Deterministic Validation Gate (`validator.ts`)

A candidate rule pack is rejected if any of the following checks fail:

1. **Manifest Integrity:** `id`, `name`, `version` (semver), `type: 'rule-pack'`.
2. **Declarative Purity:** Uses `checkDeclarativePurity()` to verify zero functions, symbols, getters/setters, prototype pollution keys (`__proto__`, `constructor`, `prototype`), circular structures, or custom class prototypes.
3. **Matcher Safety:** All property matchers must use standard operators (`equals`, `not-equals`, `contains`, `matches`, `gt`, `gte`, `lt`, `lte`, `exists`, `in`, `regex`).
4. **Regex Bounding:** Patterns used in `regex` or `matches` must compile without error and have length $\le 1,000$ characters to prevent ReDoS.
5. **Depth Limit:** AST depth must not exceed 50 levels.
6. **Engine Compatibility:** Successfully converts via `adaptRulePackToRules()` and passes `@veris/rules` `validateRuleDefinition()`.

### 4.3 Test Generation & Execution (`test-generator.ts`)

To prove that candidate rules work deterministically before review:

1. **Positive Fixture:** Generates an `EvaluationContext` with evidence/features guaranteed to satisfy the condition tree.
2. **Negative Fixture:** Generates an `EvaluationContext` with non-matching evidence/features.
3. **Engine Evaluation:** Executes `RuleEngine.evaluateRules([rule], context)`.
4. **Verification:** Validates that positive fixture produces a `RuleMatch` with expected confidence and negative fixture produces zero matches.
5. **Determinism Verification:** Executes evaluation 10 times consecutively, asserting identical match IDs and outputs.

### 4.4 Candidate Artifact Contract (`artifact.ts`)

The candidate artifact encapsulates all data required for human review:

- `candidateRulePack`: Declarative AST of the rule pack.
- `rationale`: Non-authoritative human-readable explanation of why the rule detects the condition.
- `validation`: Detailed checklist of validation checks passed.
- `testResults`: Results of the automated positive/negative test execution.
- `metadata`: Provider name, model, generation timestamp, and explicit disclaimer that AI rationale is non-authoritative.

## 5. CLI Command Contract

The CLI command is registered under `veris rule author` (with alias `veris rules author`):

```bash
# Generate a candidate rule from intent offline
veris rule author --intent "Detect cleartext API keys in configuration files" \
                  --name "Hardcoded API Key" \
                  --evidence-type "configuration" \
                  --severity high \
                  --output ./candidate-api-key.json

# Review and explicitly promote candidate rule to active plugin directory
veris rule author --promote ./candidate-api-key.json --target-dir ./.veris/plugins
```

Exit Codes:

- `0`: Success (candidate generated and tested, or candidate promoted).
- `1`: Validation or execution failure.
- `2`: Usage error (missing required arguments).
